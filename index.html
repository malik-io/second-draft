How It Works

A proposer suggests a lesson. An auditor checks it against held-out evidence in a separate context and rubric. A deterministic gate then admits, quarantines, or rolls back the lesson.

Proposer

Suggests a lesson from the agent's work.

Auditor

Checks the proposed lesson against held-out evidence in a separate context and rubric.

Deterministic Gate

Admits, quarantines, or rolls back the lesson based on the audit and evidence.

Proposed Lesson → Auditor Veto → Evidence Gate → Rollback/Commit

The gate is deterministic: a lesson is committed only after it passes the auditor and evidence checks; otherwise it is quarantined or rolled back.

What this demonstration proves, and what it doesn't

  • Proves, on the stated fixtures: a lesson can be admitted only after it passes an evidence gate, a wrong lesson can be quarantined, and a regressing lesson can be suspended and rolled back with a reversal record.
  • Does not prove: general safety, general learning, novel-failure detection, production readiness, or independent model-family validation.
  • The default local proposer is rule-based (DeterministicProposer), not open-ended autonomous lesson discovery.
  • The local fixture auditor is not a model (LocalFixtureAuditor) — it is a deterministic fixture check. Meta proposer/auditor adapters and any live API evidence are distinct from the captured fixture transcript.
  • The system stores and applies versioned lessons; it does not retrain or modify model weights.

Disclosures

  • All data shown are synthetic and entrant-authored.
  • Results are limited to the stated frozen fixtures and do not establish generalization.
  • Meta Model API integration is wired in code: proposer muse-spark-1.3, auditor muse-spark-1.1. A live call has been completed, but a labeled live transcript is not yet claimed, so no live transcript is presented here.
  • Auditor separation is by version, context, and rubric — NOT by model family. Both proposer and auditor are Muse Spark.
  • Production readiness is NOT claimed.
