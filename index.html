An agent that learns from its work — but only keeps a lesson when evidence supports it, and can reverse that lesson when it stops working.

Explore the code Read the technical notes

The idea: learning must be reversible

Agents that learn from experience need more than a memory store. They need a controlled way to decide which lessons may influence future behavior — and a way to withdraw a lesson when new evidence exposes a failure.

Propose

Distill a candidate lesson from recurring patterns in executed work.

Challenge

Check its provenance, corroboration, contradictions, and auditor assessment.

Control

A deterministic gate admits or quarantines it. Retrieval exposes admitted lessons only.

Reverse

Suspend a regressing lesson, record why, and restore an older version only after revalidation.

Trajectory→Candidate→Evidence gate→Admit or quarantine→Monitor and reverse

01 · Learn

A useful lesson earns admission

Two earlier briefing runs repeat the same verification failure. The local proposer distills a calendar-cross-check lesson. The fixture evidence supports it, and the gate admits it. The next briefing uses the authoritative calendar record.

02 · Catch a plausible falsehood

Confidence does not count as evidence

A candidate claims the 9 AM standup moved to 8 AM, with proposer confidence of 0.9. The ground-truth calendar contradicts it and corroboration is missing. The gate challenges and quarantines the candidate; retrieval excludes it.

03 · Detect regression and reverse

A lesson can be right in one context and wrong in another

A revised lesson is admitted in its weekend context, but fails regression probes on the original weekday cases. The system suspends that version, writes a reversal record, and restores the previous version only after it passes revalidation.

Implementation and evidence boundaries

  • Implemented in the local slice: versioned lesson records, append-only event log, guarded state transitions, deterministic evidence checks, admitted-only retrieval, quarantine, suspension, rollback with revalidation, A/B/C runner, and state-derived status panel.
  • Local proposer: deterministic and rule-based over recurring verifier tags. It is not open-ended autonomous lesson discovery.
  • Local auditor: a deterministic fixture stub, not a model. It enables reproducible offline tests and is labeled as such.
  • Meta integration: proposer and auditor adapters are wired to the Meta Model API (muse-spark-1.3 and muse-spark-1.1). A direct live proposer call and a live --meta demo run were reported successful; the captured fixture transcript is not a labeled transcript of those live model outputs.
  • Auditor separation: different Muse Spark versions, contexts, and rubrics; not independent model-family validation.
  • Scope: synthetic entrant-authored data and a small frozen fixture set. This demonstrates specified mechanisms on designed cases; it does not establish general safety, novel-failure detection, production readiness, or broad generalization.
  • Learning mechanism: the system stores and applies versioned lessons. It does not retrain or modify model weights.
